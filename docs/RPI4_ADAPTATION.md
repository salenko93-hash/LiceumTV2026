# Аналіз архіву та адаптація для Raspberry Pi 4

## Висновок

Початковий пакет — Python HTTP backend (стандартна бібліотека), openpyxl для Excel, qrcode для SVG, вебінтерфейс Chromium. Pi 5-специфічних GPIO/PCIe або нативних модулів не виявлено. Тому переписувати розклад чи слайд-шоу для іншого процесора не потрібно. Адаптація зосереджена на встановленні, завантаженні дисплея й обслуговуванні кіоску.

Цільовий профіль: Raspberry Pi 4 Model B, Raspberry Pi OS 64-bit Bookworm/Trixie, рекомендовано 4 GB, один TV Full HD на HDMI0. Інсталятор відхиляє іншу модель, 32-bit ОС і непідтримуваний реліз до системних змін. Pi 400/Compute Module та старі ОС цією збіркою не заявляються.

## Виявлені проблеми і зміни

1. Старі deployment-скрипти використовували Pi 5, `pi`, `192.168.1.228` і очікували версію 3.4.0, тоді як backend був 3.4.1. Тепер `INSTALL_TO_RPI4.ps1` і `CHECK_RPI.ps1` використовують `admin@192.168.2.193`, версійні написи узгоджені. Адреси QR/Mobile, HTML-приклади та JSON-шаблон оновлені.
2. Режим HDMI не обмежувався. На Pi 4 автоматичний 4K дає зайве навантаження. Інсталятор додає kernel video mode 1920×1080@60 лише для HDMI-A-1, інші аргументи і другий HDMI зберігаються. Є одноразовий backup і тест повторного застосування. Штатний KMS та Chromium GPU acceleration залишені.
3. Міграції config/calendar виконувались без sudo у системній папці. Тепер вони мають потрібні права, після чого власником даних стає користувач встановлення.
4. Health check інсталятора ігнорував помилку. Тепер є обмежене очікування й ненульовий exit при невдачі. Кіоск не запускає браузер після вичерпання очікування backend.
5. Watchdog міг перезапускати Chromium під час повільного старту. Додано 120 секунд на запуск до DevTools-перевірки; перевірка backend продовжується.
6. Додано PipeWire/WirePlumber і user-session bus для headless Chromium audio. На реальному TV треба перевірити вибраний аудіовихід.
7. Замість видалення фіксованої домашньої папки Windows installer використовує унікальну staging-папку в `/tmp`, перевіряє SSH-параметри та виділяє TTY для sudo. Staging лишається для діагностики; її можна видалити після успішного встановлення.
8. Виправлена застаріла інструкція Desktop Autologin: поточний пакет запускає Cage через systemd на tty1.

`admin` використано як ім'я SSH-користувача, не як пароль або вебключ. Наявні role-ключі й живі налаштування не переписуються. Під час перенесення вже налаштованої системи старий Mobile URL треба змінити в адмінці вручну.

## Що перевірено у хмарі

Середовище: x86_64, Python 3.12; це не емуляція Pi.

- `VERIFY_PROJECT.py`: успішно; 13 тестів (7 slideshow, 4 UI, 2 HDMI-конфігурація).
- Семантика чотирьох розкладів і SHA-256 content manifest — успішно, навчальні дані не змінені.
- `bash -n` для всіх shell-скриптів, Python compile та Node syntax для змінених JS — успішно.
- Встановлення за `requirements-dev.txt`, `pip check` і повторний запуск backend — успішно.
- HTTP 200: TV, Admin, Ops, Mobile, JS/CSS; health версії 3.4.1; state з новою Mobile URL, без секретних ключів; SVG QR; POST screen heartbeat.
- Mobile API для 10-А на 2026-10-19 повертає 7 уроків; усі 4 джерельні XLSX читаються через openpyxl.
- PowerShell-файли ASCII-сумісні. Сам PowerShell/SSH installer на Windows не виконувався.

Для перевірок локальна ігнорована `data/config.json` налаштована на loopback, без зовнішньої синхронізації й погоди. Цей файл, згенеровані ключі та runtime-дані не входять у ZIP. Production-шаблон зберігає налаштування мережевих функцій.

## Межі перевірки

На `192.168.2.193` нічого не встановлювалося. Фактичний apt install на ARM, systemd/logind, KMS/HDMI, звук, час запуску і перезавантаження потребують перевірки на Pi 4. Адресу треба закріпити у роутері; код не призначає статичний IP. Автоматичні повітряні тривоги потребують власного токена; Telegram, віддалені оновлення, OTA та погода не перевірені локальними тестами.
